# People Party — Claude Code Instructions

People Party is a multiplayer party game: a **C++ WebSocket backend** and a **Vue 3 + TypeScript
frontend**, built for big-screen gameplay with mobile phones as controllers. Client ↔ server
communication is binary, serialized with **FlatBuffers**.

Everything below has been checked against the current codebase. Where a convention has known
exceptions, they're named explicitly rather than glossed over — don't treat this file as a
formatter config; match the surrounding code.

## Adding a new minigame

Use the dedicated skills for this — each has the full step-by-step procedure, reference files to
read first, and pitfalls:

1. `create-minigame-schemas` — FlatBuffer `.fbs` files under `schemes/minigamedata/{GameName}/`
2. `create-minigame-backend` — C++ class under `backend/src/minigames/{game_name}/`
3. `create-minigame-frontend` — Vue components under `frontend/src/components/{gameName}/`

Schemas must be created and built (`npm run build:macos`/`build:nix`/`build:windows`) before the
backend/frontend skills can reference the generated `GameStateType_`/`GameStateType` enum values.

## Architecture

### Message flow

```
Client (Vue) → WebSocket → nginx (/confetti/) → Backend (C++) → Party → Game → GameState
```

- WebSocket endpoints: `/host` (creates a party) and `/join/:room/:name` (joins an existing one)
- Party IDs are 4-digit numeric codes, generated and validated in `party.cpp`/`websocket.cpp`
- Every message is wrapped in a FlatBuffer `Message` table with a `MessageType` enum + `Payload`
  union
- Frontend WebSocket store: `frontend/src/stores/confettiStore.ts` (legacy name — it manages all
  WS communication, not just a "confetti" feature)

### Game state machine

`Game` (`backend/src/game.h/cpp`) orchestrates three `GameState` subclasses:
1. **PartyPrep** — lobby, round/game selection
2. **MiniGame** — the active minigame (queued, drawn from `Game::add_minigames()`)
3. **Leaderboard** — score display between games

`GameState` declares the shared contract every state (including every minigame) must implement:
`process_input(Message*, Client*)`, `update(int delta_time)`, `clients_changed(int, bool)`, and a
protected `finished()`. `MiniGame` (`backend/src/minigames/minigame.h`) extends `GameState` and
adds its own pure virtuals — see the backend skill for the exact split, it matters when you're
deciding what to override. `finished()` is already implemented for minigames in `minigame.cpp`: it
records the leaderboard placement and advances `Game` to the next state — a minigame calls it, it
doesn't implement it.

### FlatBuffers schema system

- Schemas live in `schemes/`, auto-generated by `schemes/builder.sh` (run via `npm run build*`)
- **Phase 1**: recursively scans `schemes/minigamedata/*.fbs`, strips `"Payload"` from table names
  to build `enum GameStateType`, and emits `schemes/payloadtypes/MiniGamePayloadType.fbs`
  (enum + `union GameStatePayload`)
- **Phase 2**: scans `schemes/payloadtypes/*.fbs` (non-recursive), strips `"PayloadType"` from
  filenames to build `enum MessageType`, and emits `schemes/messageClass.fbs`
  (enum + `union Payload` + root `table Message`)
- Enum integer values depend on filesystem traversal order — **always reference by name, never by
  number**
- Generated outputs (gitignored, regenerated on every build — **never edit directly**):
  - C++: `backend/src/flatbuffer/messageClass_generated.h`
  - TypeScript: `frontend/src/flatbuffers/*.ts` (barrel: `messageClass.ts`)

## Code Standards — Backend (C++)

- **C++23**, CMake + Conan. `file(GLOB_RECURSE ...)` collects sources — nothing to register manually
- Dependencies: uWebSockets 20.71.0, FlatBuffers 24.3.25, Box2D 2.4.1 (used only by
  `marble_mania` and `teambased_pong` — not a general dependency every minigame needs), Doctest
  2.4.11 (present in Conan but its test target is fully commented out in `CMakeLists.txt` — no
  `Tests` binary is actually built; don't expect to run backend tests)
- **Header guards**: `#ifndef`/`#define`, never `#pragma once`. Most minigame headers use
  `PEOPLEPARTY_BACKEND_{NAME}_H`; several core files (`client.h`, `party.h`, `thread_timer.h`, …)
  use shorter legacy guards. Use the `PEOPLEPARTY_BACKEND_` prefix for new files
- **Naming**: classes `PascalCase`; minigame classes are usually `{Name}_MiniGame` but a few
  existing ones are `{Name}_Minigame` (`BusinessBailout_Minigame`, `LaunchParty_Minigame`,
  `RightOnTime_Minigame`) — match whichever file naming a given directory already uses, default to
  `_MiniGame` for new games since it's the majority. Same inconsistency exists in filenames:
  `_mini_game.h/.cpp` (majority) vs `_minigame.h/.cpp` — pick based on precedent, not a fixed rule.
  Methods/variables/members: `snake_case`. Minigame directories: `snake_case`
- **Formatting**: 4-space indent is standard in minigame code (some core files use 2-space).
  Function bodies commonly use Allman braces, but constructors/destructors are frequently written
  K&R-style (`Foo::Foo() : Base() {` on one line) — both appear even within the same file; match
  the file you're editing rather than forcing one style
- **Time constants**: always use the DSL macros in `backend/src/util/defines.h`, never raw
  milliseconds — `SECONDS` (`* 1000`), `MILLISECONDS` (`* 1`), `MINUTES` (`* 60 SECONDS`). Write
  `7 SECONDS`, not `7000`
- **Memory**: raw pointers with manual `new`/`delete` is the default (repositories store by value
  in `std::map` and hand back raw `T*`). The one exception is `marble_mania_map`, which uses
  `std::unique_ptr`/`make_unique` — don't treat that as license to introduce smart pointers
  elsewhere, follow the surrounding file
- **Threading**: `ThreadTimer` (`util/thread_timer.h`) — `setInterval(cb, ms)`, `setTimeout(cb, ms)`,
  `clear()`, `pause()`, `resume()` — is the only concurrency primitive; each call spawns a detached
  thread. Timer callbacks run off the uWS event loop, so raw WebSocket sends need
  `server_loop->defer(...)`; `party->send_gamestate()`/`send_message()` already do this for you —
  prefer those over sending directly. Every timer must be `.clear()`-ed in the destructor
- **Globals**: singletons in `backend/src/util/globals.h`, declared `inline`
  (`party_repository`, `client_repository`, `server_loop`)
- **Error handling**: no exceptions anywhere in `backend/src` — early `return` on null/failure.
  No logging framework — `std::cout << ... << std::endl;`
- **FlatBuffer building**: create strings/vectors *before* the table that references them, wrap in
  `MiniGamePayloadType` with the matching `GameStateType_`/`GameStatePayload_` enum pair (read
  `messageClass_generated.h` for the exact names — never guess), send via
  `game->party->send_gamestate(filter_lambda, builder, payload.Union())`
- Reference minigames worth reading: `teambased_pong` (multi-phase rounds, Box2D, team logic) and
  `shell_shuffle` (newest addition, current phase-enum pattern) are the best up-to-date examples.
  The older `shell_game` was deleted from the repo — don't reference it.

## Code Standards — Frontend (Vue 3 + TypeScript)

- **Always `<script setup lang="ts">`**, Composition API only — no Options API anywhere in the
  codebase. Section order is `<script>` then `<template>`
- **UI libraries**: Tailwind CSS utility classes for layout/spacing/typography, plus
  **Naive UI** (`naive-ui`) for structured components — `NCard`, `NScrollbar`, etc. are used
  throughout results screens, grids, and settings (e.g. `memoryMixer`, `crazyCounting`,
  `unscrambled`, `leaderboard`, `partyManagment`). Don't skip Naive UI in favor of hand-rolled
  markup where an existing component fits
- **`<style>` blocks**: prefer Tailwind, but `<style scoped>` is an accepted and common pattern for
  keyframe/CSS animations that Tailwind can't express — it appears in roughly a dozen components
  (`launchParty`, `rightOnTime`, `highwayHustle`, `marbleMania`, `teambasedPong`, `leaderboard`,
  and others), not just one. Reach for it only for animation, not general styling
- **Prettier** (`.prettierrc.json`, exactly enforced): no semicolons, single quotes, 2-space
  indent, 100-char width, no trailing commas. ESLint itself only enforces Vue/TS correctness rules
  (`@vue/eslint-config-prettier/skip-formatting` disables ESLint's own stylistic rules) — Prettier
  is the sole source of truth for formatting
- **TypeScript**: `strict: false`. `interface` for object/model shapes, `type` for unions.
  `Number()` wrap every FlatBuffer `bigint` field; `decodeURI()` every FlatBuffer string field
  (names are URI-encoded server-side). `@/` alias maps to `src/`
- **Minigame routing is fully automatic** — `GameManager.vue` loads
  `defineAsyncComponent(() => import(`./${name}/${componentName}View.vue`))` where `name` comes
  from the payload's `minigame()` string. There is **no switch/case to edit** and no manual
  registration; the directory name (camelCase) must exactly match the backend's
  `get_camel_case_name()`, and the files must be named exactly `HostView.vue`/`PlayerView.vue`
- Both views must `defineExpose({ update(data: MiniGamePayloadType) { ... } })`; by convention
  `update()` returns `[]` at the end
- **PixiJS** (`vue3-pixi` + `pixi.js` v8): `<Application>` as the canvas container, drawing done
  imperatively inside `<Graphics @render="renderFn">` (the `@render` event, not a `:draw` prop —
  there are zero uses of `:draw` in this codebase)
- **Responsive canvas sizing** (see `teambasedPong/HostView.vue` for the current pattern): track
  the container's `clientWidth` via `ResizeObserver`, derive `canvasHeight` from a fixed aspect
  ratio, and compute a `scale` factor (`canvasWidth / GAME_WORLD_WIDTH`) — multiply every drawn
  coordinate by `scale`, never hardcode pixels. `crazyCounting` instead uses
  `Math.min(width, height)` for a square canvas — pick whichever fits the game's aspect needs
- Reference components worth reading: `teambasedPong` (newest complex example — phases, joystick,
  Box2D-driven rendering) and `shellShuffle` (newest addition) alongside `highwayHustle` (PixiJS +
  sprites) and `memoryMixer` (non-canvas, Naive UI grid). `shellGame` was deleted — don't reference
  it, even if you see stray build artifacts mentioning it in `frontend/dist/`
- Routes: `host`, `join`, `info`, `releases`, defined in `frontend/src/router/index.ts` with
  lazy-loaded route components

## Code Standards — FlatBuffer Schemas

- Directory per game: `schemes/minigamedata/{GameName}/` (PascalCase). Tables: PascalCase +
  purpose suffix (`{GameName}HostPayload`, `...PlayerInputPayload`, `...ResultPayload`, etc.).
  Helper/sub-tables: `FB`-prefixed (`FBVec2`, `FBTeamPlayer`). Fields: `snake_case`
- Enums: `PascalCase` name, default underlying type `: byte`, with **`SCREAMING_SNAKE_CASE`**
  values for game constants (`TEAM_A`, `ROCK`) vs `PascalCase` for protocol-level enum values
  (`Host`, `Join`). One existing exception worth knowing about: `MarbleMania`'s `FBEntityType` uses
  `: ubyte` with PascalCase values (`Marble`, `Obstacle`) — don't copy that for new schemas, use
  the standard `: byte` + SCREAMING_SNAKE_CASE convention instead. Also avoid the raw
  `phase: byte`/`game_phase: ubyte` pattern seen in a couple of payloads that mirrors an enum
  without actually using it — declare and reuse the real enum type
- **No `namespace` declarations, no `file_identifier`** — genuinely zero exceptions across all 55
  `.fbs` files in the repo. Every schema file ends with `root_type {MainTableName};`
- Joystick-based games reuse the shared `JoystickDataPayload.fbs`/`JoystickEventPayload.fbs` at the
  root of `schemes/minigamedata/` — don't create new ones

## Development Workflows

**Full stack (Docker):**
```bash
npm run start  # installs deps, builds schemas, starts docker-compose-dev
```

**Backend only:**
```bash
cd backend
conan install . --output-folder=build --build=missing --settings=build_type=Debug
cd build && cmake .. -DCMAKE_TOOLCHAIN_FILE=conan_toolchain.cmake -DCMAKE_BUILD_TYPE=Debug
cmake --build .
./PeopleParty-Backend
```

**Frontend only:**
```bash
cd frontend
npm install
npm run dev  # binds 0.0.0.0 for mobile device testing on the same network
```

**PixiJS composable playground** (dev only, once the frontend dev server above is running):
```
open http://localhost:5173/dev/pixi-playground
```
Live reference/regression check for the `useGameCanvas`/`createEntityLayer`/`useSnapshotBuffer`
composables (`frontend/src/composables/pixi/`) — see `frontend/README.md` for what it shows and
how to read it. Dev-only route (`import.meta.env.DEV`-gated in `frontend/src/router/index.ts`),
never present in a production build.

**Schema regeneration** (required after any `.fbs` change — errors from stale generated code are
cryptic):
```bash
npm run build:macos   # or build:nix / build:windows
```

### Docker architecture

Three services: `nginx` (reverse proxy, routes `/confetti/` → backend, internal port 80),
`client` (Vue SPA, internal port 80), `api` (C++ backend, internal port 7899). Only nginx is
exposed to the host — `7789:80` in dev/prod (`docker-compose-dev.yml`, `docker-compose.yml`),
`7889:80` in staging. Production/staging pull pre-built images from `ghcr.io/kraanter/peopleparty*`
and don't publish `api`/`client` ports directly; they're only reachable through nginx's internal
proxy.

### Testing

- Frontend: Cypress is scaffolded (`npm run test:unit:dev`, `npm run test:e2e:dev`) but no tests
  are written yet
- Backend: Doctest is a Conan dependency but its CMake test target is fully commented out — there
  is currently no backend test suite to run

## Common Gotchas

- Always rebuild schemas after `.fbs` changes — stale generated code produces cryptic errors
- New minigames must be pushed into `Game::add_minigames()` in `game.cpp` — creating the class
  isn't enough to make it appear in the queue
- `get_camel_case_name()` (backend) must exactly match the frontend component directory name and
  the string used in `send_minigame_introduction()`/message builders — mismatches silently fail to
  route
- Timer callbacks run on background threads, not the uWS event loop — send through
  `party->send_gamestate()`/`send_message()`, which defer internally, rather than sending directly
- FlatBuffer strings/vectors must be created before the table that references them
- `Number()` every FlatBuffer bigint, `decodeURI()` every FlatBuffer string, on the frontend
- Never hardcode `GameStateType`/`MessageType` integer values — they depend on filesystem
  traversal order in `builder.sh`
- `GameManager.vue` needs no edits when adding a minigame — routing is automatic dynamic import,
  not a switch statement
